# i18n 经验：引用不存在的翻译 key

## ❌ 错误写法
```tsx
// 假设 'user.profile.settings' 这个 key 在 zh-CN.json 中不存在
const text = t('user.profile.settings'); // 可能返回空字符串或原 key 字符串
```

## ✅ 正确写法
```tsx
// 方案1：给默认值
const text = t('user.profile.settings', '默认文案');

// 方案2：构建时校验（推荐）
// 使用 i18next-scanner 或 react-intl 的 extract 工具，在 CI 中检查缺失 key

// 方案3：开发环境告警
if (process.env.NODE_ENV === 'development' && !i18n.exists('user.profile.settings')) {
  console.warn('Missing i18n key: user.profile.settings');
}
```

## ⚠️ 边界情况
- i18next 默认返回 key 本身作为 fallback，可能让用户看到 `user.profile.settings` 这种原始字符串
- 某些库（如 next-intl）在开发模式会抛错，生产模式静默返回 key——行为不一致要注意
- 动态拼接 key（如 `t(\`user.${type}\`)`）无法被静态分析工具检测，需额外测试
- 嵌套命名空间（如 `t('a.b.c.d')`）在扁平化翻译文件中会找不到，注意文件组织结构
- SSR 场景下，服务端和客户端的水合过程需要保证 i18n 实例和语言包完全一致，否则会出现 hydration mismatch
